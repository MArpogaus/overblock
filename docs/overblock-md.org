#+TITLE: How overblock-md works
#+OPTIONS: toc:2

This document describes the API and the implementation. The
[[file:../README.org][README]] tells you how to use the package. The
block layer under it is another package of this repository:
[[file:overblock.org][its notes]].

The package has two files. =overblock-md.el= turns markup into one
propertized string and shows nothing. =overblock-md-preview.el= is a
minor mode that shows a Markdown buffer over its own source. It gives
the three answers that the live cycle asks for.

* Markup rendered

=overblock-md-rendered= takes markup and gives one propertized string.

| Function                        | What it does                                     |
|---------------------------------+--------------------------------------------------|
| =overblock-md-rendered=         | markup in, one propertized string out            |
| =overblock-md-html-batch-async= | convert many texts in one process                |
| =overblock-md-render-regions=   | render the regions of a buffer in one process    |
| =overblock-md-columns=          | the columns that a window gives a rendering      |
| =overblock-md-program=          | the converter that is installed, or nil          |
| =overblock-md-follow-link=      | open the URL of a rendered link that was clicked |
| =overblock-md-eglot-renderer=   | render the documentation of a language server    |

** The converter

=overblock-md-command= names the command that turns Markdown into
HTML. The candidates are in this order:

1. =pandoc --mathjax --no-highlight --wrap=none -f markdown-implicit_figures=
2. =markdown_py -x tables -x fenced_code=
3. =cmark-gfm -e table=
4. =markdown=
5. =cmark=

The candidates that can do a table and a code fence come first. Each
one leaves the math alone for the preview images:

- =--mathjax=, because plain =pandoc= renders a formula itself, and the
  inline math is then lost.
- =--wrap=none=, because a line that pandoc wraps can cut a formula in
  two.
- =--no-highlight=, because shr reads no CSS class. The colours of
  pandoc are lost, and only the time to load the syntax definitions
  stays.
- =-f markdown-implicit_figures=, because pandoc otherwise puts an image
  alone in a paragraph into a =figure= with a =figcaption=. shr has no
  handler for it, and the alt text shows twice.

=markdown_py= without its extensions turns a table into one line of
pipes. =cmark= and Perl =markdown= cannot do a table or a fence.
=overblock-pydoc-command= asks pandoc for the same; see
[[file:overblock-pydoc.org][its notes]].

shr reads the HTML with libxml2. Without libxml2 the markup stays
plain text. =overblock-pycell-mode= tells which part is missing, and
the other modes give no message.

=overblock-md-html-batch-async= sends many texts to the converter in
one call, and does not wait for the answer. It puts a marker between
the texts and cuts the HTML at that marker. One process for a buffer is
much faster than one for each region. Where the number of pieces is
not the number of texts, a caller converts each text alone.

=overblock-md-render-regions= sends one batch of a kind at a time. A
cycle that comes while the batch is with the converter waits. When the
batch lands, the live cycle of that kind runs again. A batch first
shows the regions that a window shows. A timer then shows the rest,
=overblock-md--slice= (fifty) at a time, so a large buffer does not
hold the reader. A rendering that signals ends the flight of its batch,
so the next cycle of that kind does not wait for good. A batch shows
its regions over the whole buffer, also under a narrowing.

The answer is nil where no converter is installed, and where the
converter exits with an error. The check is where the program is
called and not in each caller. A signal from a minor mode body would
leave the mode on with nothing rendered, and stop the rest of the hook.

** Images

shr fetches an image with =url-queue-retrieve=, which answers after the
rendering is done. A rendering in a temporary buffer then keeps the
grey placeholder of shr.

Thus =overblock-md--tag-img= draws a file itself, through
=shr-external-rendering-functions=. The alt text carries the image, so
a terminal still tells what is there. An image named by URL is fetched
once into the folder =overblock-images/= of the XDG cache folder
(=~/.cache= by default), and drawn from there. A URL that failed is
not asked for again in the session, until
=overblock-md-forget-failed-images=. With =overblock-md-remote-images=
nil, the package fetches nothing and shows such an image as its alt
text. shr does not get it, because shr would fetch it.

A terminal draws no image, and the placeholder of shr is itself an
image that hides the text under it. Thus where images cannot show, the
label goes in as text: the alt text, or the file name in brackets.

The cap of an image is the work of the layer: =overblock-image-cap= and
=overblock-image-height=, in [[file:overblock.org][the notes of the
layer]].

** Links

A rendering is a display string. =shr-browse-url= reads the URL at
point, which is buffer text, and point cannot be on a display string.
Thus each link of a rendering gets =overblock-md-link-map= in place of
=shr-map=. =<mouse-2>= runs =overblock-md-follow-link=, which reads the
URL from the clicked string. The parent is =shr-map=, whose
=follow-link= makes =mouse-1= on a link do the same. Thus a click
(=mouse-1= or =mouse-2=) on a rendered link opens it. A click on other
text of a block shows its source.

An image inside a link keeps the link. shr puts the link around what
the renderer inserted, and =overblock-fill-props= writes the keymap of
a block only where the rendering has none.

** Formulas

A =$...$= or =$$...$$= fragment becomes a preview image.
[[https://github.com/alberti42/latex-to-svg-backend][latex-to-svg-backend]]
makes it. It runs =latex= and =dvisvgm= in a process of its own. It
compiles each equation once, and keeps a cache by the content of the
equation. Nothing waits. A fragment that still compiles shows as text,
and the =overblock-md-pending= property marks it. It shows as an image
when the image arrives.

The engine is asked from the buffer that shows the rendering, and not
from the temporary buffer of shr. The engine reads its options in that
buffer. Thus a preamble that a project sets in =.dir-locals.el= applies,
and a failed equation warns once for that buffer. The font height also
comes from that buffer, so the formulas follow =text-scale-adjust=
without a new compile. The colour is the foreground of the face in the
variable =overblock-md-math-face=, =default= by default.
=overblock-pydoc= binds it to =font-lock-doc-face=, so the formulas have
the colour of the doc string. A theme change draws each formula again in
the new colour.

What the converter renders stays text, and only the rest becomes an
image. pandoc renders simple math as text. Such text loses its
=\(= and =\)= delimiters, and keeps the dollars.

A formula inside a table is an image with a stretch after it. The
stretch makes up the width of the marks, so the row keeps its columns.

A formula that fails stays text. The engine reports the failure once,
with the log of LaTeX. =latex-to-svg-backend-invalidate= forgets one
equation, so that it compiles again.

** Tables

shr renders a table without rules, and gives a header cell and inline
code no face of their own. The renderer draws =th= in bold and =code=
in =overblock-md-code=, through =shr-external-rendering-functions=. The
columns and the bold header carry the table, without rules.

A table is laid out in characters and not in pixels. Thus its columns
align over the fixed-pitch lines of a buffer, and a face cannot move
them.

** Code blocks

A fenced block that names its language gets the font lock of that
language. =overblock-md-code-modes= maps the names that do not spell
their mode. Each other name is tried as =LANGUAGE-mode=, through
=major-mode-remap-alist=. With the option nil, each block wears
=overblock-md-code=.

** The width of a rendering

shr fills a paragraph to a width. A rendering happens in a temporary
buffer that no window shows, and shr then fills to the width of the
frame. A block is usually narrower, so the rows would run past the
edge of the window.

Thus the mode that renders binds =overblock-md-width=, because it knows
where its block is. =overblock-md-columns= measures the room: the
columns of the narrowest window that shows the buffer, less the indent
of the block, less one column. A row that fills the last column wraps.
The answer is never less than twenty columns.

Nil is a legal answer, and a buffer in no window gives it. shr then
fills as it does by itself. The layer renders the blocks again when the
buffer changes width; see [[file:overblock.org][its notes]].

** A language server's documentation

=overblock-md-eglot-renderer= is a value for
=eglot-documentation-renderer=. eglot calls the renderer in a temporary
buffer with the Markdown of the server, and then runs
=font-lock-ensure=. The function puts =overblock-md-rendered= of the
text in place of the text, and sets =font-lock-fontified=. Thus the
=font-lock-ensure= that follows keeps the faces.

The function changes one thing in the Markdown first. A server writes
its signature in a fence, a rule of three dashes under it, and the
first paragraph under the rule. pandoc reads a rule, text and then a
setext underline as one simple table. A blank line after the rule
prevents this.

The function keeps up to two hundred renderings by their text, because
eldoc asks again after each move. A rendering that waits for a formula
is not kept. A theme change and a change of =overblock-md-eldoc-width=
empty the table.

* The preview mode

=overblock-md-preview-mode= is =overblock-live-start= with three
answers: which regions, what to render them with, and when. The layer
shows the rendering, hides the source under it, and removes it on an
edit. The mode works only where the major mode derives from
=markdown-mode=. It stays off while =overblock-rmd-mode= is on, because
that mode renders the prose through the same cycle.

** Which regions

The unit is the Markdown block and not the line, because a line of
Markdown is often not Markdown alone. The lines of a table, of a fence
and of a list render wrong one at a time. The whole block goes to the
converter, and the rendering is put back over its lines, one piece for
each line.

A block is a fenced code block, or else the run of lines between two
blank lines. =overblock-md-preview-fences= finds the fences first.
=overblock-md-preview-paragraphs= then walks the buffer with those
bounds. It jumps over a fence, so a blank line inside a fence ends no
paragraph. A fence also ends the paragraph that touches it, as in
CommonMark. Thus prose with no blank line before a fence is a block of
its own. A fence indented under a list item belongs to that item, and
the item goes on after it.

A backtick fence with another backtick on its line is inline code and
opens no block. Outside a list item, a fence four or more spaces in is the text of an
indented code block and opens no block. A closing fence is at most
three columns deeper than its opening fence. A later paragraph of a
list item ends at the next item. Alone, the converter reads that item
as more text of the paragraph, and the item loses its bullet.

Under a list item, a block goes to the converter without the spaces
that indent its first line. Thus a fence under a later paragraph is not
deeper than the line before it, and does not become inline code. Only
spaces go, and a tab stays for the converter to read. Elsewhere the
indentation stays, because it makes a code block.

The walk starts at the top of the buffer, because only that tells
whether a region starts inside a fence. A fence that is not closed runs
to the end of the buffer.

=overblock-md-preview-regions-function= is buffer-local. It is called
with the bounds to look at, and gives the regions in order.
=overblock-rmd= sets it to the prose only, because the chunks are run
and not rendered. The two walks are public for the same reason.
=overblock-rmd= takes its chunks from =overblock-md-preview-fences=.

** When, and at what cost

=overblock-md-preview-render-buffer= sends the whole buffer through one
converter process, and does not wait. A block converts alone where the
answer does not have a marker between each pair.

=overblock-live-wanted-p= is asked twice: once to choose what to send,
and again when the answer arrives. The reader can click, type and move
while the process runs.

A rendering comes off on each edit under it, through
=overblock-stale-when-edited=. This includes the typing of the reader,
a replacement over the buffer, a macro and an undo. Point that moves
onto a rendering does not remove it. The region point is in stays
source until point leaves it, because the mode keeps
=overblock-live-source-at-point= at t.

A block that renders to nothing, such as YAML front matter or a lone
HTML comment, stays as it is and is not blanked. It gets an empty
block all the same, so the live cycle does not convert it again.

* The tests

- =test/overblock-md-test.el=: the converter, the batch of texts, the
  math previews, the tables in characters, and the images. The image
  tests check which paths name a file, and that the file shows. They
  also check that a link on an image keeps the click, and how a remote
  image is fetched.
- =test/overblock-md-preview-test.el=: what one Markdown block is, a
  fence inside a paragraph, and the source of the region at point. It
  also tests the edit that removes a rendering, an answer that arrives
  far from point, and the mode that leaves nothing behind.

A fifth of all tests render markup, and skip where no converter is
installed. =make test STRICT=1= makes such a skip a failure, and the CI
sets it.
