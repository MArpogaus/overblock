#+TITLE: How pycell works
#+OPTIONS: toc:2

This document describes the implementation.  The [[file:../README.org][README]] tells you how
to use the package.

The text uses these terms:

- *cell*: a piece of a Python file between two cell markers.
  code-cells finds the markers.
- *block*: what pycell shows over a region of the buffer, or after it.
  A result is one, a rendered markdown cell is another.
- *shell*: the inferior Python process that =python.el= starts.
- *mirror*: the copy of the output that the block shows.

* How a result gets into the buffer

=python-shell-send-string= puts the code into =__PYTHON_EL_eval=.
This function returns the value of a trailing expression.  The value
goes through the display hook of IPython, where comint-mime has its
renderers.

The output therefore goes into the REPL as before.  pycell only
mirrors it:

1. It puts a marker at =process-mark= before it sends the cell.
2. It waits for the next prompt.
3. It copies the region up to the prompt out of the REPL.  The copy
   keeps the text properties, and therefore the images.

What the REPL shows is not what a copy of it shows, and two things
have to change on the way out:

- *The stretches.* comint-mime renders a DataFrame as a vtable, which
  sets the width of a space in pixels measured for the window of the
  REPL.  shr, in a markdown cell, says where a space ends instead.
  Both land elsewhere in a block that is shown indented, so each
  stretch becomes as many real spaces as it is characters wide.  A
  vtable measures its header in its own face, so those widths are
  fractions of a character and a header label can stand a column left
  of its data.
- *The bindings.* A vtable carries the keymap of a live table, and no
  binding of it can find a table in a copy.  The =keymap=,
  =local-map=, =mouse-face= and =help-echo= properties therefore go:
  a block must not offer a click it cannot answer.

** A table in a block, and a table in a buffer

The copy of a vtable carries the table object in its =vtable= text
property, and that object holds the columns and the rows.  pycell reads
them and lays the table out again for the block: each column as wide as
its widest cell, in characters, and the names of the columns in bold.
Nothing in that layout can be moved by a face, which the stretches of
the original could: a vtable measures a header cell in the face of a
header, so a copy shown in another face had its header squashed and its
rows apart.

=pycell-pop-output= does not copy that text.  It calls =vtable-insert=
with the table object, so the buffer holds a table that vtable drew for
that window: sorting, narrowing and moving a column all work there.
The block stays a fast, aligned, plain rendering; the buffer is where a
reader sorts.

The result rides the newline that ends the cell; the block layer below
puts it there.

pycell writes nothing into the buffer.  Files, LSP and undo see no
change.  There is one exception: the last cell of a buffer gets a
final newline if it has none, because the block needs that character.

** The block layer

Results and rendered markdown cells are two callers of one layer, which
knows nothing of Python, cells or markdown: a caller renders text and
hands it over.  It is three files, and everything they own is named
=overblock-=, so they can leave for a package of their own without a
rename:

- =overblock.el= — the blocks themselves, and the bars, buttons and
  glyphs a header is made of.
- =overblock-md.el= — markdown in, one propertized string out.
- =overblock-repl.el= — the output of a shell, cut loose from that
  shell.

What stays in =pycell.el= is the part that knows about Python: the
cells, the process, the commands, and what a prompt of that shell looks
like.

#+begin_src emacs-lisp
  (overblock-show BEG END
                  :kind 'result          ; whose block this is
                  :data ANYTHING         ; what the caller keeps with it
                  :over TEXT             ; shown instead of the region
                  :body TEXT             ; shown after the region
                  :header TEXT :footer TEXT
                  :hidden t              ; show nothing for now
                  :keymap MAP :help-echo STRING
                  :attached OVERLAYS)    ; the caller's own
#+end_src

An anchor overlay covers the region and holds those properties.  It
stops before the newline that ends the region, so a window which starts
at the next line keeps the block out of view; a second overlay covers
that newline and carries what shows after it.
=overblock-refresh= makes everything the block shows anew from the
properties, so nothing has to be saved and given back — that is how a
fold takes a markdown cell off the screen and gives it back with
=:hidden=.

Where each row goes was decided by measurement, in a graphical frame:

- The header and the footer are strings of their own.  A bar puts its
  icons at the window edge with =(space :align-to (- right ...))=, and a
  display property ignores that spec: the icons then sit beside the
  label.
- A plain body rides the =display= property of the newline, which costs
  least.
- A body with an image cannot: display properties do not nest, so the
  image is swallowed.  Such a body hides the newline with an empty
  display string and draws in the =after-string= beside it.
- The first row takes a line break only where the newline it hangs on
  does not already begin a line, so a cell that ends in a blank line
  gives that line to its header.
- =overblock-fringe=, an option rather than a keyword, draws a line
  down the left fringe of every block, two pixel columns wide as
  =org-modern= draws one.  A =line-prefix= on an overlay says nothing
  about the rows of a string, so each row carries its own; a bracketed
  body therefore rides a string rather than the display property, where a
  prefix draws nothing.  Feet at the two ends are left out: such a bitmap
  lands beside the right row where the row is a line of the buffer, and
  one row off where the row belongs to a string.

Text shown =:over= a region hangs on its lines, a piece to a line, and
lines with no piece left for them go under a cloak.  That is what makes
a tall rendering scroll a line at a time; see [[#the-cost-of-a-rendered-markdown-cell][the cost of a rendered
markdown cell]].

** The header bars

=pycell-result-buttons= and =pycell-markdown-buttons= hold the buttons
of the two bars — the shape that =overblock-button-type= asks customize
for — and =overblock-buttons= walks a list of them.  A
descriptor names the glyph candidates rather than one glyph, because
=overblock-glyph= asks the frame which of them it can draw and a
terminal answers differently from a graphic frame.  Keep the plain
candidates apart from each other: in a terminal that draws no arrows,
=^= for the button that pops a result out and =^= for the one that
moves a cell up would be the same button to a reader.

The fold arrow and the spinner are not in those lists.  They are not
buttons of the reader's choosing: they say what the result is doing.

* Moving a cell

=code-cells-move-cell-down= transposes the text of two cells with
=transpose-regions=, which leaves an overlay where the text used to
be: the result of one cell would end up under the other.
=pycell-move-cell-down= therefore reads what both cells show, lets
code-cells move the text, and puts each block back on the cell it
belongs to.  The new bounds come from the lengths, as
=transpose-regions= leaves them:

- Moving down, the cell ends where the other one ended.
- Moving up, it starts where the other one started.

Point keeps its offset inside the cell that moved, so a repeated click
on a header button keeps moving the same cell.  A rendered markdown
cell is rendered again after the move, because its pieces hang on the
source lines and those lines have moved.

The command signals before it takes anything off: code-cells refuses
to move the first cell up or the last one down, and a refused move
leaves the buffer as it was.

* The live mirror

A ticker runs each 0.2 seconds while a cell runs.  It shows the
output so far, a spinner and a stopwatch.

The block shows at most =pycell-max-lines= lines, and these are the
first lines of the output.  The ticker therefore reads only the head
of the output:

- =pycell--output-head= reads the first lines and cleans them.  It keeps the
  text as soon as all lines that show are there.  The ticks after
  that read nothing.
- =pycell--total= counts the new lines only.  It keeps the position
  that it reached in the run state.

An earlier version read the whole output on each tick.  The cost grew
with the cell.  A cell with 60000 lines paid 25 ms for a tick at the
start and 101 ms at the end.  A cell with 200000 lines did not
finish.  The bounded mirror stays at 1 ms for both.

The finished cell goes through one full read.  The result and the
line count are therefore exact.

* Cells with IPython syntax

A cell can hold syntax that only IPython reads: a magic such as
=%matplotlib inline=, a shell escape such as =!ls=, or a help request
such as =print?=.  jupytext files hold such cells.

=pycell--ipython-syntax-p= reads the buffer with =syntax-ppss=.  Only
a line at the top level counts.  A continuation line inside brackets
can start with a modulo sign.  A comment can end with a question
mark.  A cell of plain Python must not go down the IPython road,
because a shell without IPython answers with a =NameError=.

Such a cell goes to =get_ipython().run_cell=.  pycell sends the code
as base64, because this keeps quotes and newlines safe.  Two things
follow: the tracebacks count the lines from the top of the cell, and
a shell without IPython reports that it does not know =get_ipython=.

* Markdown cells

A cell with the marker =# %% [markdown]= renders in place.

The rendering hangs on the source lines, one piece to a line.  A cell
therefore has a height in lines and moves as normal text.  An earlier
version drew the whole cell as one display string, and the view then
jumped by a whole cell.

The pieces cover the text of the line only.  A line that has no piece
goes under a cloak.  A cloak is an invisible overlay that starts at
the newline of the line above.  An invisible run that starts inside a
line, or a line of no height, stops =scroll-down= with a
=beginning-of-buffer= error in the middle of the cell.

The cell keeps the height of its source, or it becomes shorter.  A
three line table can render as one line, and the spare lines then go
under a cloak.

A piece that holds an image cannot ride a display property, because
display properties do not nest and the image would be swallowed.  Such
a piece hides its line with a display string of nothing, which is not
an invisible run, and rides the after-string, which draws images.  The
line keeps its own row, so a cell with a preview scrolls a line at a
time like any other.  An earlier version gave the whole cell one
string as soon as one image was in it, and a machine with LaTeX
therefore scrolled markdown worse than one without.

** The converter

=overblock-md-command= names the command that turns Markdown into
HTML.  pycell looks for =markdown=, =pandoc=, =markdown_py=, =cmark=
and =cmark-gfm=, in this order.

shr reads the HTML with libxml2.  Without libxml2 the markdown cells
stay plain text, and the mode reports which part is missing.

=overblock-md-html-batch= sends all cells of a buffer to the converter in one
call.  It puts a marker between the cells and splits the HTML at that
marker.  One call for a buffer is much faster than one call for each
cell.  pycell falls back to one call per cell if the number of pieces
does not match the number of cells.

** Images

shr fetches an image with =url-queue-retrieve=, which answers long after
a cell is rendered: a cell rendered in a temporary buffer keeps the grey
placeholder shr leaves in the meantime.  Measured with a relative path,
an absolute one and a =file://= URL alike, every local image stayed a
placeholder.

=overblock-md--tag-img= therefore draws a file itself, through
=shr-external-rendering-functions=.  The alt text carries the image, so
a terminal still says what is there, and the figure is capped from the
window as a result's figure is.  An image on the network is left to shr,
which shows its own box for what it cannot fetch in time.

An image inside a link keeps the link: shr wraps whatever the renderer
inserted, and =overblock-fill-props= writes the block's keymap only where
the rendering has none of its own.

A terminal draws no image, and shr's placeholder is itself an image: its
display property swallows the text under it and leaves a blank row where
a figure belongs.  So where images cannot be drawn the label goes in
plainly — the alt text, or the file's name in brackets where there is
none.

** Formulas

A =$...$= or =$$...$$= fragment becomes a preview image.  The images
live in =~/.cache/overblock-math=.

The formulas take the shortest road.  What the converter renders
stays text.  Only the rest becomes an image.  pandoc renders simple
math as text by itself.

A formula inside a table stays text as well.  A table is padded to the
width of its text, and an image is never as wide as the text it
replaces, so a row with a preview in it would stand out of line.  The
table rendering marks the text it covers and the formula pass leaves
marked text alone.

** Tables

shr renders a table without rules, and it gives a header cell and
inline code no face of its own: its answer for code is a fixed pitch,
which says nothing in a buffer that is fixed pitch throughout.  pycell
renders =th= in bold and =code= in =overblock-md-code= through
=shr-external-rendering-functions=.

The rules are shr's to draw and it draws them badly here: a frame
around a frame, one per cell, and a ragged end to every row.  The
columns and the bold header carry the table instead.

* Scrolling

A result block is one buffer line, because it is one display string.
=next-line= and =previous-line= cross it in one step.  A window can
start at a buffer position only.

A block that holds an image is worse.  Display properties do not
nest, so such a block rides on the after-string of the overlay, and a
window cannot start inside an overlay string.  Three measurements on
a notebook of forty cells with one such block:

- The wheel does not cross the block in a symmetric way.  Twenty
  crossings of six events of 25 pixels bring a block of plain text
  back to the pixel.  A block with an image ends 26 characters and 69
  pixels lower.
- A block that is taller than the window throws the wheel back.  A
  figure at 0.9 of a text area of 437 pixels bounced 40 times in 399
  events and never passed.  =overblock-image-height= therefore caps
  an inline figure at 0.8 of the window.  The same figure then passes
  in 94 events.
- =scroll-up-line= does not pass such a block at all.  From the top
  of the buffer it stopped after 119 commands, and the next 40
  commands changed nothing.  The same buffer without the block
  reaches the end in 134 commands.

These commands do pass: =scroll-up= and =scroll-down=, which move a
page, and =next-line=, which moves point.  A folded block also
passes.  =pycell-pop-output= shows the figure in a buffer of its own.

** The cost of a rendered markdown cell
:PROPERTIES:
:CUSTOM_ID: the-cost-of-a-rendered-markdown-cell
:END:

A rendered markdown cell makes each scroll event more expensive.
Measured on =demo/scrolling.py= in a window of 1000x700 pixels: 2.0
ms for an event downwards and 4.9 ms upwards.  The same file with the
blocks off needs 0.6 ms and 1.0 ms.

The cost comes from the face runs, and not from the height.  Rendered
Markdown holds several hundred face runs in a line.  Source code
holds a few.  Forty lines of plain output scroll as fast as none, and
twelve lines with many face changes cost three times as much.

=M-x pycell-md-unrender= gives the plain source and the speed back.
=pycell-md-render-all= brings the blocks back.

* What the hot paths cost

Three audits read this package with no history of it, and their findings
were measured before and after on the same inputs.

The output of a running cell, cleaned and shown five times a second:

| what                              | before   | after   |
|-----------------------------------+----------+---------|
| clean 100000 characters, one line | 47.2 ms  | 3.3 ms  |
| clean 10000 lines                 | 420.9 ms | 28.5 ms |
| find the table in 10000 lines     | 637.9 ms | 0.0 ms  |
| one tick over 100000 on one line  | 68.1 ms  | 1.1 ms  |

- =overblock-repl--table-at= walks the runs of the =vtable= property, not the
  characters of the output.
- =pycell--clean= copies through a temporary buffer only where the text
  carries a display property, which is what a rendering leaves behind.
  Its two `replace-regexp-in-string' passes ask a search first, since
  that function copies its argument twice whether it matches or not.
- =pycell--output-head= is bounded in characters as well as in lines,
  which is what took a tick from 68 milliseconds to one.  The bound holds
  only where no escape sequence begins inside it: comint-mime sends an
  image as one, and a cut inside it drops the figure — measured, a result
  of no characters at all.
- =overblock-repl-first-lines= looks at the lines that show and stops;
  =overblock-repl-count-lines= counts only where the number is not known yet.
- =pycell--show= keeps the block it has when only the data changed,
  which is every tick of a running cell.

And what a keypress does, which is where the rest of the cost was:

| what                                     | before | after  |
|------------------------------------------+--------+--------|
| move one markdown cell among sixty       | 69 ms  | 18 ms  |
| fold a result of 10000 lines, four times | 13 ms  | 0.6 ms |

- =pycell-md-render-all= takes a region, and =pycell-move-cell-down=
  passes the span of the two cells that moved rather than rendering every
  markdown cell in the buffer.
- A result counts its lines once and keeps the number in its record, so
  a fold reads it instead of scanning the output again.
- =overblock--pieces= deals its rendered lines off a walking list
  rather than with =seq-subseq= from the front, which was quadratic in
  the lines of a cell: 2.7 milliseconds at a thousand against 0.3 at
  three hundred.
- =overblock-fill-props= takes a plist and walks the rendering once, where
  =pycell--fill-prop= walked it once for every property.

The scrolling was measured with bursts of wheel events shaped like a
flick of a trackpad, over forty cells with results, figures and rendered
markdown, under the author's own configuration:

| what                      | ms an event      | a sweep to the end | reversals |
|---------------------------+------------------+--------------------+-----------|
| this package              | 2.1 down, 1.2 up | 1391 ms            |         0 |
| the code before the layer | 2.7 down, 3.7 up | 1834 ms            |         0 |

The two were measured one after the other, on the same notebook and the
same frame.  A bracket in the fringe costs about three times as much an
event, because a bracketed body rides a string rather than a display
property; nothing in this package asks for one.

* The tests

=make test= runs the batch suites, one to a file, and a test sits with
the code it checks:

- =test/overblock-test.el= — which slot each row lands in, the line
  break the first row takes and the one it does not, a hidden block and
  its return, blocks of two kinds in one region, what a delete takes
  with it, the cloak that reaches the last line, the prefixes of the
  bracket, and the bars, buttons and glyphs.
- =test/overblock-md-test.el= — the converter, the batch of cells, the
  math previews, the tables laid out in characters, and the images:
  which paths name a file, that the file is drawn rather than shr's
  placeholder, that a link on an image keeps the click, and that a
  remote image stays shr's business.
- =test/overblock-repl-test.el= — a copied table laid out again, its
  getter, and the images capped.
- =test/pycell-test.el= — the clean of the output, the body lines, the
  cell markers, the folds, the edit buffers, the mirror, and moving a
  cell.

A test that names only what the layer owns moved to the layer's suite; a
test that goes through pycell's own commands stayed with pycell.

=test/overblock-client-test.el= is a second caller of that layer,
and a test rather than a feature: it renders the math in a Python
docstring over the lines of the docstring, with no process behind it and
no cell.  It answers one question — does a caller of another shape need
anything the layer does not have — and so far it needs nothing.

=make scroll= needs a graphic display.  It builds a buffer with
markdown cells and scrolls through it with
=pixel-scroll-precision-scroll-up= and
=pixel-scroll-precision-scroll-down=.  The test fails on three
things:

- The window moves against the direction of the scroll.
- The scroll command signals in the middle of a cell.
- The end of the buffer stays out of reach.

The test uses the default values of the scroll options.  The package
does not change these options.
