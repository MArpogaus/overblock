#+TITLE: How overblock works
#+OPTIONS: toc:2

This document describes the implementation.  The
[[https://github.com/MArpogaus/overblock][README]] tells you how to use the package.

The text uses these terms:

- *block*: what the layer shows over a region of the buffer, or after
  it.
- *anchor*: the overlay that covers the region and holds the state.
- *caller*: whatever renders the text.  The layer renders nothing.
- *piece*: one line of a rendering, hung on one line of the source.

* The block layer

A caller renders text and hands it over:

#+begin_src emacs-lisp
  (overblock-show BEG END
                  :kind 'result          ; whose block this is
                  :data ANYTHING         ; what the caller keeps with it
                  :over TEXT             ; shown instead of the region
                  :body TEXT             ; shown after the region
                  :header TEXT
                  :hidden t              ; show nothing for now
                  :keymap MAP :help-echo STRING
                  :attached OVERLAYS)    ; the caller's own
#+end_src

An anchor overlay covers the region and holds those properties.  It
stops before the newline that ends the region, so a window which starts
at the next line keeps the block out of view; a second overlay covers
that newline and carries what shows after it.

=overblock-refresh= makes everything the block shows anew from the
properties, so nothing has to be saved and given back — that is how a
fold takes a rendering off the screen and gives it back with
=:hidden=.

The buffer text never changes.  Files, undo and a language server see
nothing.  There is one thing a caller has to know: a block needs a
newline to hang a body on, so a caller whose region is the last of the
buffer has to write that character.

** Where each row goes

Decided by measurement, in a graphical frame:

- The header is a string of its own.  A bar puts its icons at the
  window edge with =(space :align-to (- right ...))=, and a display
  property ignores that spec: the icons then sit beside the label.
- A plain body rides the =display= property of the newline, which costs
  least.
- A body with an image cannot: display properties do not nest, so the
  image is swallowed.  Such a body joins the header on the
  =after-string= of the anchor.  The newline is never hidden: with the
  rows of a figure on its after-string and the newline itself replaced
  by an empty display string,
  =pixel-scroll-precision-scroll-up= refused to pass the block — 280
  refusals over six figures.
- The first row takes a line break only where the newline it hangs on
  does not already begin a line, so a region that ends in a blank line
  gives that line to its header.

** Text shown over a region

Text shown =:over= a region hangs on its lines, a piece to a line, and
lines with no piece left for them go under a cloak.  That is what makes
a tall rendering scroll a line at a time.

A cloak is an invisible overlay that starts at the newline of the line
above.  An invisible run that starts inside a line, or a line of no
height, stops =scroll-down= with a =beginning-of-buffer= error in the
middle of the rendering.

The rendering keeps the height of its source, or it becomes shorter.  A
three line table can render as one line, and the spare lines then go
under a cloak.

A piece that holds an image cannot ride a display property, for the
reason above.  Such a piece hides its line with a display string of
nothing, which is not an invisible run, and rides the =before-string=,
which draws images.  The before-string and not the after-string: a
cloak begins where the piece ends, and Emacs leaves out an overlay
string whose position is inside invisible text — measured by the pixels
of the image itself, 0 on the after-string against 32 on the
before-string.  The line keeps its own row, so a rendering with a
preview in it scrolls a line at a time like any other.  An earlier
version gave the whole region one string as soon as one image was in
it, and a machine with LaTeX therefore scrolled markup worse than one
without.

** What an edit takes down

=overblock-stale-when-edited= puts three hooks on a block and not one:
=modification-hooks= runs for a change inside an overlay,
=insert-in-front-hooks= for one at its first character and
=insert-behind-hooks= for one at its end.  An anchor stops one
character short of the newline that ends its region, so the blank line
that ends the region — where =C-e= on the last line puts point — is an
insertion at the end: with =modification-hooks= alone the block stayed
behind, showing a rendering of text that had changed under it.

=overblock-sweep-orphans= removes what is left when text is cut out
from under a block: the pieces outlive the anchor that owned them.

* The header bars

=overblock-buttons= walks a list of descriptors.  A descriptor names
the glyph candidates rather than one glyph, because =overblock-glyph=
asks the frame which of them it can draw and a terminal answers
differently from a graphic frame.  Keep the plain candidates apart from
each other: in a terminal that draws no arrows, =^= for the button that
pops something out and =^= for the one that moves something up would be
the same button to a reader.

Emacs can ask a font what it holds and a terminal nothing, so a
terminal is given the plain last candidate of every list.  A reader
whose terminal does carry the icon font sets
=overblock-terminal-glyphs=; the coding system is still asked, so a
terminal that cannot encode a candidate never gets it.

** A bar in place of a line

=overblock-bar-over= makes the overlay and =overblock-bar-draw= draws
on it.  All of the bar but its last character rides the
=before-string=; the last character is the =display=, in place of the
line's own text, and carries =cursor=.

Both halves are forced.  The bar has to be a string on an overlay: a
display property whose value is a string ignores =(space :align-to (-
right ...))=, and the buttons would then sit beside the label instead of
at the window edge.  And something has to be left for the caret to draw
on: over a display of the empty string there is no glyph, so point could
stand on the line with nothing to show it, and the line could not be
folded from.  The stretch aligns to the window's right edge, so moving
one character out of the string moves nothing.

Never the =after-string=: a string after the overlay draws at the
overlay's *end*, and a rendering's cloak covers that place.  A
rendering at the top of a buffer is the worst of it — its cloak begins
at the line's own newline — and the bar drew as one glyph and nothing
else.

A bar is rebuilt only when the line it stands on or the width of the
window has changed.  Both are in the key the overlay carries, so a
caller that draws from a change hook pays a comparison for a line that
only moved: measured over two hundred bars, 0.003 ms for one line
against 38.7 ms for a change of width, which rebuilds every one.

** A column of slack

=overblock-bar= holds the buttons one column short of the right edge in
a graphic frame, as it always did two columns short in a terminal.
Ending at the edge exactly leaves redisplay to decide whether the row
wraps, and it decides differently at different moments: measured in one
window at one width, the same bar drew all of its buttons when the
buffer was opened and put the last one on a row of its own after the
first command — same string, same specification, same window.

A terminal keeps a third column for the ellipsis an outline fold hangs
after the line.

** Point on the line

A bar stays where it is, whatever point does.  It used to give way to
its line while point was on it, and that cost more than it paid: the
buffer moved under the reader as point crossed the line, and a button
went dead — a press moves point, the bar was gone before the release,
and the release then landed on the text the bar had covered.

The line is still there to be edited.  Point rests on it, the caret
shows on the bar's last glyph, and the label follows what is written on
the line.  Folding works from there.

The commands hang off =<down-mouse-1>= with =<mouse-1>= bound to
=ignore=, which is what the header line buttons of a side window have
always done: the press is answered before anything can redraw under the
pointer.

** The width a bar is cut to

=overblock-window-width= answers with the narrowest *visible* window
that shows the buffer.  =visible= and not t: an invisible or iconified
frame counts under t, and a buffer shown in the root window of a hidden
20 column frame had its header cut to that.

A buffer in no visible window is not cut at all.  There is nothing to
wrap in, and the cut is baked into the string: measured, a long
rendering built while the reader looked at another buffer had its header
cut to the width of that buffer's window — down to " ▾…" — and the cut
stayed there when the buffer came back into a window of 160 columns.

The measurement saves point.  =window-max-chars-per-line= and its like
select the window they measure, which sets this buffer's point to that
window's point, and nothing puts it back when the buffer is not the
selected window's.  A caller that walks the buffer with point was sent
back to a line it had passed and drew for ever: measured at 99.5% of a
core and 91 GB of memory in a buffer edited while the reader looked
elsewhere.

* The live cycle

=overblock-live-start= is the whole of a mode that keeps a buffer
rendered and editable.  The caller answers three questions: which
regions, what to render them with, and when.

The render function is called once at the start and then whenever the
reader stops moving, after =IDLE= seconds of quiet.  It must leave
alone what is rendered already and the region point is in — the reader
is editing that one, and rendering it would take the text out from
under them.

A rendering comes off when the reader clicks it and when the text under
it is edited.  Point arriving somewhere reveals nothing: a reader
scrolls through a buffer, and a rendering that came off under the window
made the text grow and shrink as they went.

A mode that sends a whole buffer of regions through one converter does
so from that one function, which is why the layer asks for a function
of no arguments rather than one for each region.

* The edit buffer

=overblock-edit-in-buffer= opens the text under a block in a buffer of
its own, as =org-edit-special= opens a source block.  The caller says
what to call it, which mode it wears, how to read the text out and how
to write it back.

A buffer for each region and not one for the whole file: the text of the
region opened second would otherwise land on top of the first, and an
hour of writing with it.

An edit of this very region that is already under way is the edit the
reader wants back, not a fresh copy of what the file still says; org
answers the same, by asking.  The same region and not merely the same
name: a name carries a line number, and two regions can stand on that
line at different times.  Keeping a stranger's pending edit committed
one region's text into another, and throwing it away without a word
would lose an hour of writing just as quietly, so the reader is asked.

* Markup rendered

=overblock-md-rendered= is markup in, one propertized string out.
Nothing in it shows anything.

** The converter

=overblock-md-command= names the command that turns Markdown into
HTML.  The candidates are =pandoc --mathjax --no-highlight=,
=markdown_py -x tables -x fenced_code=, =cmark-gfm -e table=,
=markdown= and =cmark=, in this order: the ones that can carry a table
and a code fence first, and each one told to leave the math for the
preview machinery.  Plain =pandoc= renders a formula itself, which left
a document with no inline math at all.

=--no-highlight= because shr reads no CSS class, so the colours pandoc
encodes in one are dropped and the only thing that survives its
highlighting is the line anchor it hangs on each row of a code block.
Measured on a document of 216 lines with three fenced blocks, pandoc
spent 785 milliseconds of which 720 were the syntax definitions it
loaded to paint them.  =overblock-pydoc-command= asks for the same for
the same reason, with reStructuredText first, because that is what
Python's own tools read.

shr reads the HTML with libxml2.  Without libxml2 the markup stays
plain text, and the mode reports which part is missing.

=overblock-md-html-batch= sends many texts to the converter in one
call.  It puts a marker between them and splits the HTML at that
marker.  One process for a buffer is much faster than one for each
region: 44 milliseconds a region with =markdown_py=, which is two
seconds for fifty and nine for two hundred.  A caller falls back to one
call apiece if the number of pieces does not match the number of texts.
=overblock-md-html-batch-async= does not wait for the answer.

A converter is a process that can fail, and the answer is nil where
none is installed and nil where the one that is exits non-zero.  That
check belongs where the program is called and not in each caller: a
caller renders from the body of a minor mode, and a signal from here
left the mode on with nothing rendered and took the rest of the hook
that turned it on with it.

** Font lock as the renderer

=overblock-md-fontified= runs a major mode's own font lock over the
text and keeps what it painted, which is how eldoc shows what a
language server sends it.  =rst-mode= knows a reStructuredText section
and =gfm-view-mode= the markup of Markdown, and each leaves the text
where the writer put it, so the rendering is exactly as tall as the
source and no line below it moves.

What a converter does better: it knows the markup it is given, lays a
table out in columns and fills a paragraph to the window.  What the
font lock does better: it costs no process and keeps the lines as
written.

** Images

shr fetches an image with =url-queue-retrieve=, which answers long after
a rendering is done: a rendering made in a temporary buffer keeps the
grey placeholder shr leaves in the meantime.  Measured with a relative
path, an absolute one and a =file://= URL alike, every local image
stayed a placeholder.

=overblock-md--tag-img= therefore draws a file itself, through
=shr-external-rendering-functions=.  The alt text carries the image, so
a terminal still says what is there, and the figure is capped from the
window.  An image named by URL — the Colab badge a notebook opens with
— is fetched once into =~/.cache/overblock-images= and drawn from there
like a local one; a URL that failed is not asked for again in the
session.  Set =overblock-md-remote-images= to nil to leave such an
image to shr.

An image inside a link keeps the link: shr wraps whatever the renderer
inserted, and =overblock-fill-props= writes the block's keymap only
where the rendering has none of its own.

A terminal draws no image, and shr's placeholder is itself an image:
its display property swallows the text under it and leaves a blank row
where a figure belongs.  So where images cannot be drawn the label goes
in plainly — the alt text, or the file's name in brackets where there is
none.

** The image cap

=overblock-image-height= caps an inline figure at a share of the
window, because a block taller than the window cannot be scrolled past.
Measured in a 437 pixel text area, 25 pixels a step: a figure at 0.9 of
the area bounced 40 times in 399 steps and never got past, one at 0.8
went by in 94 steps without a single step backwards.

The share is taken from the window that shows the buffer, or from the
selected window where none does: a block can be drawn while its buffer
is off screen, and no window at all would mean no cap.

Emacs 31 slices an image taller than =shr-sliced-image-height= into a
row for each line of the window it was rendered in, and a slice reads
as =((slice X Y W H) IMAGE)=.  Slicing does not make an image smaller,
so a figure sliced for a tall window and shown in a shorter one is
exactly the block the wheel cannot get past.  Nor can the image be
capped under the slice: the fractions were worked out against the height
it had.  So a run of slices of one image becomes the whole image again,
capped.

** Formulas

A =$...$= or =$$...$$= fragment becomes a preview image.  The images
live in =~/.cache/overblock-math=.

The formulas take the shortest road.  What the converter renders stays
text.  Only the rest becomes an image.  pandoc renders simple math as
text by itself.

A fragment that stays text is read as text, and pandoc with MathJax
wrote =\(x_1\)=: the parentheses say nothing to a reader, so the
delimiters come off and the dollars stay.

A formula inside a table stays text as well.  A table is padded to the
width of its text, and an image is never as wide as the text it
replaces, so a row with a preview in it would stand out of line.  The
table rendering marks the text it covers and the formula pass leaves
marked text alone.

A fragment whose preview fails stays text and the failure is remembered
for the session: what caches a preview is the image file, so without
that a rendering costs one LaTeX run per fragment every time.
=overblock-md-forget-failed-previews= asks again.

** Tables

shr renders a table without rules, and it gives a header cell and
inline code no face of its own: its answer for code is a fixed pitch,
which says nothing in a buffer that is fixed pitch throughout.  The
renderer draws =th= in bold and =code= in =overblock-md-code= through
=shr-external-rendering-functions=.

The rules are shr's to draw and it draws them badly here: a frame
around a frame, one per cell, and a ragged end to every row.  The
columns and the bold header carry the table instead.

A rendered table is laid out in characters rather than pixels, so its
columns line up over the fixed-pitch lines of a buffer.  Nothing in
that layout can be moved by a face, which shr's own stretches could.

* The output of a shell

=overblock-repl-detach= cuts a copy of shell output loose from the
shell it came from.  Three things have to change on the way out:

- *The stretches.* comint-mime renders a DataFrame as a vtable, which
  sets the width of a space in pixels measured for the window of the
  shell.  shr says where a space ends instead.  Both land elsewhere in
  a block that is shown indented, so each stretch becomes as many real
  spaces as it is characters wide.  A vtable measures its header in its
  own face, so those widths are fractions of a character and a header
  label can stand a column left of its data.
- *The table.* The copy carries the table object in its =vtable= text
  property, and that object holds the columns and the rows.  The layer
  reads them and lays the table out again: each column as wide as its
  widest cell, in characters, and the names of the columns in bold.
  =overblock-repl-table-copy= gives a caller the object for another
  buffer, where =vtable-insert= draws a live table and every binding of
  vtable works.
- *The keymap.* The copy carries the keymap of the shell, and a block
  must not offer a click it cannot answer.

=overblock-repl-first-lines= looks at the lines that will show and
stops; =overblock-repl-count-lines= counts only where the number is not
known yet.  A caller's own limit is a natnum, so zero is a legal value,
and a scan that counts from one never met a limit of zero and read the
whole result instead — measured, 18.6 milliseconds and a full copy over
twenty thousand lines.

* Scrolling

A body is one buffer line, because it is one display string.
=next-line= and =previous-line= cross it in one step.  A window can
start at a buffer position only.

A body that holds an image is worse.  Display properties do not nest,
so such a body rides on the after-string of the anchor, and a window
cannot start inside an overlay string.  Three measurements on a buffer
of forty regions with one such block:

- The wheel does not cross the block in a symmetric way.  Twenty
  crossings of six events of 25 pixels bring a block of plain text back
  to the pixel.  A block with an image ends 26 characters and 69 pixels
  lower.
- A block that is taller than the window throws the wheel back.  See
  [[#the-image-cap][the image cap]].
- =scroll-up-line= does not pass such a block at all.  From the top of
  the buffer it stopped after 119 commands, and the next 40 commands
  changed nothing.  The same buffer without the block reaches the end
  in 134 commands.

These commands do pass: =scroll-up= and =scroll-down=, which move a
page, and =next-line=, which moves point.  A folded block also passes.

** The cost of a rendering

A rendering makes each scroll event more expensive.  Measured in a
window of 1032x700 pixels: 1.5 ms for an event downwards and 2.5 ms
upwards, against 1.0 ms and 1.4 ms for the same buffer with the blocks
off.  The numbers a reader gets depend on the machine; the ratio does
not.

The cost comes from the face runs, and not from the height.  Rendered
markup holds several hundred face runs in a line.  Source code holds a
few.  Forty lines of plain text scroll as fast as none, and twelve
lines with many face changes cost three times as much.

* What the hot paths cost

Measured before and after, on the same inputs, in a graphic frame with
the nerd font the bars are drawn in:

| what                  | before   | after    |
|-----------------------+----------+----------|
| =overblock-glyph=     | 0.010 ms | 0.001 ms |

=overblock-glyph= asks =internal-char-font= once for every character of
every candidate, and a header of six buttons asked it twenty times,
five times a second, for an answer that cannot change while the frame
keeps its font.  The answers are now kept in a table keyed by that font
and the candidates.

- =overblock--pieces= deals its rendered lines off a walking list
  rather than with =seq-subseq= from the front, which was quadratic in
  the lines of a region: 2.7 milliseconds at a thousand against 0.3 at
  three hundred.
- =overblock-fill-props= takes a plist and walks the rendering once,
  where the code before it walked the rendering once for each property.
- =overblock-show= keeps the block it has when only the data changed,
  which is every tick of a caller that shows a growing text.
- =overblock-repl-first-lines= and =-count-lines= are bounded, as
  above.

* The tests

=make test= runs the batch suites, one to a file, and a test sits with
the code it checks:

- =test/overblock-test.el= — which slot each row lands in, the line
  break the first row takes and the one it does not, a hidden block and
  its return, blocks of two kinds in one region, what a delete takes
  with it, the cloak that reaches the last line, the sweep of what lost
  its anchor, the images capped and unsliced, and the bars, buttons and
  glyphs.
- =test/overblock-md-test.el= — the converter, the batch of texts, the
  math previews, the tables laid out in characters, and the images:
  which paths name a file, that the file is drawn rather than shr's
  placeholder, that a link on an image keeps the click, and that a
  remote image stays shr's business.
- =test/overblock-repl-test.el= — a copied table laid out again, its
  getter, and the images capped.
- =test/overblock-md-preview-test.el= — what counts as one Markdown
  block, the fence inside a paragraph, the line at point showing its
  source, the edit that drops a rendering, the answer of an
  asynchronous conversion landing nowhere near point, and the mode
  leaving nothing behind.
- =test/overblock-pydoc-test.el= — which strings are documentation and
  which are data, the indentation taken off, both renderers, the bar
  and the rule, and the mode leaving nothing behind.

=test/overblock-client-test.el= is a caller of a shape the package
never wrote: it renders the math in a Python doc string over the lines
of that doc string, with no process behind it and no mode.  It answers
one question — does a caller of another shape need anything the layer
does not have — and so far it needs nothing.

A fifth of the suite renders markup and skips itself where no converter
is installed.  =make test STRICT=1= makes that a failure instead, and
the CI sets it.
