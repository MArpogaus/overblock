#+TITLE: How overblock-pycell works
#+OPTIONS: toc:2

This document describes the implementation. The
[[file:../README.org][README]] tells you how to use the package.

The text uses these terms:

- *cell*: a piece of a Python file between two cell markers. code-cells
  finds the markers.
- *block*: what overblock-pycell shows over a region of the buffer, or
  after it. A result is one, and a rendered markdown cell is another.
- *shell*: the inferior Python process that =python.el= starts.
- *mirror*: the copy of the output that the block shows.

Two packages of this repository do the work that is not Python.
overblock puts a block on the screen and holds the run loop of both
notebooks ([[file:overblock.org][its notes]]). overblock-md turns markup
into a string that a block can show ([[file:overblock-md.org][its
notes]]). This document is about the part that knows Python. The other
notebook, [[file:overblock-rmd.org][overblock-rmd]], runs R chunks
through the same loop.

* How a result gets into the buffer

=python-shell-send-region= sends the cell. The value of a trailing
expression goes through the display hook of IPython, where comint-mime
has its renderers.

The output goes into the REPL as usual. overblock-pycell only mirrors
it:

1. It puts a marker at =process-mark= before it sends the cell.
2. It waits for the next prompt.
3. It copies the region up to the prompt out of the REPL. The copy
   keeps the text properties, and thus the images.

These three steps belong to =overblock-run=, because the loop is the
same for each language. This package gives the loop a plist:
=overblock-pycell--backend=. It tells how to reach the interpreter, how
to send a cell and what a prompt looks like. It also tells how to clean
the output, and which button option a result reads. The slots are in
[[file:overblock.org][the notes of the layer]].

The copy must change before a block can show it. =overblock-repl-detach=
makes those changes; see the layer notes. A vtable keeps its table
object in the copy. Thus =overblock-run-pop-output= calls
=vtable-insert= with that object, and the buffer holds a live table
where sorting, narrowing and moving a column work. The block stays a
plain rendering in characters.

The result is on the newline that ends the cell. overblock-pycell writes
nothing into the buffer, with one exception. The last cell of a buffer
gets a final newline if it has none, because the block needs that
character.

** The header bars

The package has four button options:

- =overblock-pycell-result-buttons=, on the bar of a result.
- =overblock-pycell-cell-buttons=, on the bar of a code cell.
- =overblock-pycell-md-buttons=, on the bar of a rendered markdown cell.
- =overblock-pycell-source-buttons=, on the bar of a markdown cell that
  shows its source.

Each is a list in the shape that =overblock-button-type= gives to
customize, and =overblock-buttons= reads it.

The first five buttons of a result come from
=overblock-run-result-buttons=, with the words for a cell. A chunk of an
Rmd file shows the same five. The pair that moves a cell belongs to
this notebook, and each of the four lists ends with it. The pair is at
the end, so it is at the same place on each bar.

The fold arrow and the spinner are not in those lists. They tell what
the result does, and the reader does not choose them.

** The bar over a boundary line

A cell has a bar in place of its =# %%= line. The label is the name
after the marker, and the buttons are =overblock-pycell-cell-buttons=.
=overblock-pycell--cell-bars= draws the bars of code cells. A rendered
markdown cell has the bar of its block.

The overlay, its strings, the width it is cut to and what point does
to it belong to the layer: see [[file:overblock.org][its notes]].

*** What draws them, and when

=after-change-functions= draws them, and not =jit-lock=. One error in
another jit-lock function stops the rest. A =python-ts-mode= buffer
whose grammar does not match the mode signals from redisplay, and then
no bar would show. Thus the bars are drawn once when the mode starts,
and again over the lines that a change touched.

=overblock-bar-draw= rebuilds a bar only when its line, its label or
its icons change. Thus the change hook costs a comparison for a line
that only moved. A change of width marks each bar stale, and
=overblock-pycell--bar-redraw= draws them again.

*** One line, one bar

Three things can want a bar on a boundary line. They are the pass over
the buffer, the rendering of a markdown cell, and the pass after an
edit.
=overblock-pycell--sole-bar= keeps the bar that belongs to the line,
and removes each other one. Each kind of line has its bar:

| The line                          | The bar                        |
|-----------------------------------+--------------------------------|
| no longer a boundary              | none                           |
| =# %% [markdown]=, rendered       | the bar of the block, markdown |
| =# %% [markdown]=, showing source | source, with a render button   |
| =# %%=                            | code                           |

A bar is looked for on its whole line and not at one position. Text
typed at the start of the line moves the overlay off that start. Thus
typing before the marker is not typing inside the bar.

* The restart

=python-shell-restart= kills the process and waits for its last
output. A shell that has not prompted yet sends its first prompt into
that wait, and the setup of python.el then waits for ever on the dead
process: Emacs freezes until =C-g=. Thus =overblock-pycell-restart=
deletes the process at once, and =python-shell-make-comint= starts a
new one in the same buffer, under its name, so a shell dedicated by
hand stays so. The first-prompt filter of python.el needs point at the
end of that buffer. =comint-exec= puts it there, and each window of the
shell goes there too: a window scrolled up would give its point back
at the next redisplay.

* Moving a cell

=code-cells-mode= puts the cell boundaries into =outline-regexp=. Thus
a cell is an outline subtree, and =outline-move-subtree-down= moves it.
It cuts the text out and puts it back. It also writes the final newline
that a last cell can lack.

=overblock-pycell-move-cell-down= reads what both cells show, moves the
text, and puts each block back on its cell. After the outline move,
point is where the moved cell now begins. Thus the two new ranges are read from the buffer, and
are not counted from the old positions.

The move must know three things:

- The move starts at the boundary line of the cell. =code-cells-mode=
  also puts the headings of the major mode into =outline-regexp=. Thus
  a =def= inside a cell is a heading too, and a move from inside it
  would stop with "Cannot move past superior level".
- =overblock-pycell--stale-when-edited= does nothing while the move
  runs. The text lands at the first character of the cell that the
  moved cell passes. Without this, that cell would lose its result.
- The rest of the blocks of the moved cell is swept, because its text
  was cut out.

Point keeps its offset in the cell that moved, so a second click on a
button moves the same cell again. A rendered markdown cell renders
again after the move, because its source lines have moved.

The command signals before it removes anything. outline refuses to
move the first cell up or the last one down, and a refused move leaves
the buffer as it was.

* The live mirror

A ticker runs each 0.2 seconds while a cell runs. It shows the output
so far, a spinner and a stopwatch. The ticker and its bounds belong to
the runner: =overblock-run-output-head= reads the head of the output,
and =overblock-run-total= counts the lines as they arrive.

This package tells what an IPython prompt looks like and how to clean
it away. =overblock-pycell--clean= removes the prompts and the =Out[N]=
labels, and makes a copy that a block can show.

The head of the output is bounded in lines and in characters. The
character bound applies only where no escape sequence starts inside it.
comint-mime sends an image as an escape sequence, and a cut inside it
would lose the figure.

=overblock-pycell--clean= copies through a temporary buffer only where
the text carries a display property. Its =replace-regexp-in-string=
passes first search, because that function copies its argument even
when nothing matches. A result counts its lines once and keeps the
number, so a fold does not count again. A move renders the two cells
that moved, and no other markdown cell.

* Cells with IPython syntax

A cell can hold syntax that only IPython reads. Examples are a magic
such as =%matplotlib inline=, a shell escape such as =!ls=, and a help
request such as =print?=. jupytext files hold such cells.

=overblock-pycell--ipython-syntax-p= reads the buffer with
=syntax-ppss=. Only a line at the top level counts. A continuation line
inside brackets can start with a modulo sign, and a comment can end
with a question mark. A cell of plain Python must not go to IPython
this way, because a shell without IPython answers with a =NameError=.

Such a cell goes to =get_ipython().run_cell=, base64 encoded, which
keeps quotes and newlines safe. Thus the tracebacks count lines from
the top of the cell, and a shell without IPython reports that it does
not know =get_ipython=.

* Markdown cells

A cell with the marker =# %% [markdown]= renders in place. The
rendering is on the source lines, one piece for each line. Thus a cell
has a height in lines and moves as normal text.

The cell keeps the height of its source, or becomes shorter. A table of
three lines can render as one line, and the spare lines go under a
cloak. The cloak, the pieces and the image on a before-string belong to
the layer ([[file:overblock.org][its notes]]). The converter belongs to
overblock-md ([[file:overblock-md.org][its notes]]).

The live cycle of the layer renders the cells, as it renders the prose
of a Markdown file. =overblock-pycell-render-buffer= renders what is
not rendered yet. The whole buffer goes to the converter in one
process, through =overblock-md-render-regions=, and nothing waits for
it. A cell that the converter fails on shows its markdown as it is,
and goes to the converter again only after an edit. The mode sets =overblock-live-source-at-point= to nil, so a rendered
cell stays rendered when point moves into it. A click with =mouse-1=
shows the source until point leaves the cell. A moved cell renders at
once.

Point cannot be on a link, because it never enters a display string.
Thus =overblock-pycell-md-follow-link= reads the links of the rendering
and offers them. A click on a link uses the link keymap of
overblock-md.

* Scrolling

A result block is one buffer line, because it is one display string. A
block with an image is harder to scroll through. The reasons are in
[[file:overblock.org][the notes of the layer]].
=overblock-run-pop-output= shows the figure in a buffer of its own.

A rendered markdown cell makes each scroll event more expensive. The
cost comes from the face runs and not from the height. Turn the mode
off to get the plain source and the speed back.

* The tests

=make test= runs the batch suites, one for each file.
=test/overblock-pycell-test.el= belongs to this package. It tests the
clean of the output, the body lines, the cell markers and the folds. It
also tests the edit buffers, the mirror, and the move of a cell. A test
that names only what another package owns is in the suite of that
package.

=make test-live= sends real cells to a real IPython and reads back what
the blocks show. No batch test of this package starts a Python
process. Where no ipython is installed, the target says so and passes.

=make scroll= needs a graphic display. It builds a buffer with markdown
cells and scrolls through it with =pixel-scroll-precision-scroll-up= and
=pixel-scroll-precision-scroll-down=. It uses the default values of the
scroll options. The test fails when:

- The window moves against the direction of the scroll.
- The scroll command signals in the middle of a cell.
- The end of the buffer stays out of reach.

The first check runs on Emacs 30 and later only. On Emacs 29,
=pixel-scroll-precision-scroll-up-page= can leave point outside the
window. Redisplay then recenters, and the window moves back a little.
Emacs 30 puts point back inside the window before redisplay, and the
emacs-29 branch does not have that change. The other two checks run on
each version.
