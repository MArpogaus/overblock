#+TITLE: How overblock-pycell works
#+OPTIONS: toc:2

The [[file:../README.org][README]] tells you how to install the
package, and [[*Use][Use]] tells how to use it. The rest of this
document describes the implementation.

The text uses these terms:

- *cell*: a piece of a Python file between two cell markers. code-cells
  finds the markers.
- *block*: what overblock-pycell shows over a region of the buffer, or
  after it. A result is one, and a rendered markdown cell is another.
- *shell*: the inferior Python process that =python.el= starts.
- *mirror*: the copy of the output that the block shows.

Two packages of this repository do the work that is not Python.
overblock puts a block on the screen and holds the run loop of both
notebooks ([[file:overblock.org][its notes]]). overblock-md turns markup
into a string that a block can show ([[file:overblock-md.org][its
notes]]). This document is about the part that knows Python. The other
notebook, [[file:overblock-rmd.org][overblock-rmd]], runs R chunks
through the same loop.

* Use

** Cells

A bar stands in place of each =# %%= line. The bar shows the name that
you write after the marker. A cell without a name is /python/. These are
the buttons of =overblock-pycell-bar-buttons=:

| Button | Command                           | Action                       |
|--------+-----------------------------------+------------------------------|
| =⇈=    | =overblock-run-above=             | run each cell above this one |
| =▷=    | =overblock-run-this=              | run this cell                |
| =⇊=    | =overblock-run-below=             | run this cell and each below |
| =⌃=    | =overblock-pycell-move-cell-up=   | move this cell up            |
| =⌄=    | =overblock-pycell-move-cell-down= | move this cell down          |

A button acts on the cell of its bar. The line under the bar is still
there. Point can go on it, and the bar follows what you write. Folding
works from that line.

** Results

The bar of a result shows a spinner and a stopwatch while the cell
runs. After the run it shows the line count and the time. A cell that
fails shows =error= on its bar. A cell that printed nothing shows /no
output/. The bar shows =⚠= when the interpreter stops during the run.

The fold arrow =▾= is at the left of the bar, and the buttons of
=overblock-pycell-result-buttons= are at the right:

| Button | Command                        | Action                                 |
|--------+--------------------------------+----------------------------------------|
| =▾=    | =overblock-run-toggle-output=  | fold or unfold the result              |
| =□=    | =overblock-run-interrupt=      | interrupt this cell, and stop the pass |
| =↧=    | =overblock-run-save-image=     | save the image of the result to a file |
| =◫=    | =overblock-run-copy-output=    | copy the result, with the images       |
| =↗=    | =overblock-run-pop-output=     | show the full result in its own buffer |
| =✕=    | =overblock-run-discard-output= | discard the result                     |

The move buttons =⌃= and =⌄= of [[*Cells][Cells]] come after them. The
interrupt button shows while the cell runs, and the discard button
when the run has ended.

=overblock-run-pop-output= opens the result in a buffer of its own. A
table there is a live vtable, so you can sort it with =S=. The buffer
follows a cell that still runs. =overblock-run-interrupt= and
=overblock-run-stop= also work in that buffer.

=overblock-run-interrupt= stops the cell and the cells queued after
it. =overblock-run-stop= lets the cell finish and empties the queue. A
pass over several cells stops at the first error. At the end of a
pass, the echo area says =overblock-pycell: done=, or
=overblock-pycell: stopped at error= after a cell that failed. An
interrupt says =overblock-pycell: interrupted=, with the number of
cells it left unrun. A pass that ends with done, and scrolled to its
end, puts point and the view back where you asked for it. A failed
cell leaves them on that cell. The interrupt button leaves the view
where it is. A key that you press in the notebook during a pass gives
point and the view back. The key then acts there, not at the cell that
runs, and a stop key does the same. A scroll or a click in the
notebook moves on from the view you see, and stops the scrolling. A
cell you ask for while another runs, or while the interpreter starts,
waits its turn. The echo area then says
=overblock-pycell: this cell queued=, or =N cells queued= for a pass,
which counts its markdown cells too.

A cell can hold IPython syntax, such as =%matplotlib inline=, =!ls= or
=print?=. Such a cell goes to IPython as it is. Its tracebacks count
lines from the top of the cell. An interpreter without IPython cannot
run it.

** Markdown cells

A cell with the marker =# %% [markdown]= renders in place. Its bar
shows /markdown/ and the buttons of =overblock-pycell-md-buttons=. =✎=
edits the cell in its own buffer. The move buttons =⌃= and =⌄= come
after it. A click (=mouse-1= or =mouse-2=) on a rendered link opens it.
On other text, =mouse-1= shows the source, and =mouse-2= opens the edit
buffer. =overblock-md-follow-link= opens a link from the keyboard.

A markdown cell that shows its source has a bar with the buttons of
=overblock-pycell-source-buttons=. Its =⟳= button renders the cell.

The Markdown features are those of
[[file:overblock-md.org][overblock-md]].

** Commands

| Command                             | Action                                                                         |
|-------------------------------------+--------------------------------------------------------------------------------|
| =overblock-pycell-mode=             | turn the mode on or off for a buffer                                           |
| =overblock-pycell-mode-maybe=       | a hook function: the same, in a Python buffer only, for =code-cells-mode-hook= |
| =overblock-run-restart=             | restart with the environment of the notebook, and remove the results           |
| =overblock-run-restart-and-run-all= | restart, then run each cell in order                                           |
| =overblock-run-above=               | run each cell above this one                                                   |
| =overblock-run-below=               | run this cell and each cell below it                                           |
| =overblock-run-stop=                | stop the pass after the cell that runs now                                     |
| =overblock-run-clear-results=       | remove each result                                                             |
| =overblock-pycell-render-buffer=    | render each markdown cell that is not rendered                                 |
| =overblock-pycell-md-render-cell=   | render the markdown cell at point                                              |
| =overblock-live-edit=               | show the source of the markdown cell at point                                  |
| =overblock-pycell-md-edit=          | edit the markdown cell in its own buffer                                       |
| =overblock-md-follow-link=          | follow a link of the rendered cell                                             |

The package binds only the mouse on its bars and blocks. These keymaps
bind no key, so you can bind your own. The edit buffer of a markdown
cell uses =overblock-edit-mode-map=, with =C-c C-c= and =C-c C-k=.

| Map                         | Where it answers                   |
|-----------------------------+------------------------------------|
| =overblock-pycell-mode-map= | the notebook, while the mode is on |
| =overblock-run-result-map=  | inside a cell that shows a result  |
| =overblock-run-pop-map=     | a result in its own buffer         |
| =overblock-pycell-md-map=   | a rendered markdown cell           |

The parent of =overblock-run-pop-map= is =special-mode-map=, so =q=
quits the buffer of a result. As for the [[file:overblock.org::*Change the buttons][buttons]], put
the keys in the =:config= of the package.

#+begin_src emacs-lisp
  (keymap-set overblock-pycell-mode-map "C-c C-k" #'overblock-run-interrupt)
  (keymap-set overblock-pycell-mode-map "C-c C-q" #'overblock-run-stop)
  (keymap-set overblock-run-pop-map "i" #'overblock-run-interrupt)
  ;; TAB at the end of a cell folds its result, and does its usual work
  ;; elsewhere.
  (keymap-set overblock-run-result-map "TAB"
              '(menu-item "" overblock-run-toggle-output
                          :filter overblock-run-tab-filter))
#+end_src

** Options

| Option                            | Default       | Meaning                                    |
|-----------------------------------+---------------+--------------------------------------------|
| =overblock-pycell-result-buttons= | seven buttons | the buttons on the bar of a result         |
| =overblock-pycell-bar-buttons=    | five buttons  | the buttons on the bar of a code cell      |
| =overblock-pycell-md-buttons=     | three buttons | the buttons on a rendered markdown cell    |
| =overblock-pycell-source-buttons= | three buttons | the buttons on an unrendered markdown cell |

For the button format, see [[file:overblock.org::*Change the buttons][Change the buttons]]. The result
limits are the options of [[file:overblock.org::*Options, faces and buttons][overblock]].

** Comparison with other packages

- [[https://github.com/emacs-jupyter/jupyter][emacs-jupyter]] uses the
  Jupyter protocol and the =zmq= module, with kernels for many
  languages. =overblock-pycell= uses the Python interpreter of
  =python.el=.
- [[https://github.com/astoff/code-cells.el][code-cells]] gives the
  cells and the commands. =overblock-pycell= adds the output.
- [[https://github.com/millejoh/emacs-ipython-notebook][EIN]] edits
  =.ipynb= files. =overblock-pycell= edits plain Python files, which
  are easy to diff.

* How a result gets into the buffer

=python-shell-send-region= sends the cell. The value of a trailing
expression goes through the display hook of IPython, where comint-mime
has its renderers.

The output goes into the REPL as usual. overblock-pycell only mirrors
it:

1. It puts a marker at =process-mark= before it sends the cell.
2. It waits for the next prompt.
3. It copies the region up to the prompt out of the REPL. The copy
   keeps the text properties, and thus the images.

These three steps belong to =overblock-run=, because the loop is the
same for each language. This package gives the loop a plist:
=overblock-pycell--backend=. It tells how to reach the interpreter, how
to send a cell and what a prompt looks like. It also tells how to clean
the output, and which button option a result reads. The slots are in
[[file:overblock.org][the notes of the layer]].

The copy must change before a block can show it. =overblock-repl-detach=
makes those changes; see the layer notes. A vtable keeps its table
object in the copy. Thus =overblock-run-pop-output= calls
=vtable-insert= with that object, and the buffer holds a live table
where sorting, narrowing and moving a column work. The block stays a
plain rendering in characters.

The result is on the newline that ends the cell. Thus the last cell
needs a final newline, as [[*Known limits]] says.

** The header bars

[[*Options]] lists the four button options, and [[*Results]] the
buttons of a result. The first five buttons of a result come from
=overblock-run-result-buttons=, with the words for a cell. A chunk of an
Rmd file shows the same five. The pair that moves a cell belongs to
this notebook, and each of the four lists ends with it. The pair is at
the end, so it is at the same place on each bar. The fold arrow and
the spinner are in no option, because they tell what the result does.

** The bar over a boundary line

[[*Cells]] tells what the bar of a cell shows. =overblock-pycell--bar=
is the =:bar= of the backend, and draws the bar of one boundary line. A
rendered markdown cell has the bar of its block.

The overlay, its strings, the width it is cut to and what point does
to it belong to the layer: see [[file:overblock.org][its notes]].

*** What draws them, and when

=overblock-run--bars= draws them when the mode starts, and again when
the reader stops, as in the Rmd notebook. Thus a bar arrives a moment
after its line is written. The bar cycle does not depend on =jit-lock=.
One error in a jit-lock function stops the rest, and a =python-ts-mode=
buffer whose grammar does not match the mode signals from redisplay. See
[[file:overblock.org][the notes of the layer]].

=overblock--bar-draw= rebuilds a bar only when its line, its label or
its icons change. Thus a walk over the cells costs a comparison for
each bar that did not change. A change of width marks each bar stale,
and the runner draws them again.

The source bar of a markdown cell comes at once when its rendering
comes off, and does not wait for the reader to stop.

*** One line, one bar

Two things can want a bar on a boundary line. They are the walk over
the cells and the rendering of a markdown cell. A line has one bar:
=overblock-bar-line= removes each other bar of the line, and the walk
removes the bar of a line that is no boundary. Each kind of line has
its bar:

| The line                          | The bar                        |
|-----------------------------------+--------------------------------|
| no longer a boundary              | none                           |
| =# %% [markdown]=, rendered       | the bar of the block, markdown |
| =# %% [markdown]=, showing source | source, with a render button   |
| =# %%=                            | code                           |

A bar is looked for on its whole line and not at one position. Text
typed at the start of the line moves the overlay off that start. Thus
typing before the marker is not typing inside the bar.

* The restart

=python-shell-restart= kills the process and waits for its last
output. A shell that has not prompted yet sends its first prompt into
that wait, and the setup of python.el then waits on the dead process
until =C-g=. Thus =overblock-pycell--restart=, the =:restart= of the
backend, deletes the process at
once, and =python-shell-make-comint= starts a new one in the same
buffer, under its name, so a shell dedicated by hand stays so. The
command is the one of the notebook, also where the interpreter had
died: an environment switched in the notebook takes effect at the
restart. A command typed with =C-u C-c C-p= does not survive it,
because python.el keeps no sign of which command was typed.

The first-prompt filter of python.el needs point at the end of the
shell buffer. =comint-exec= puts it there, and each window of the
shell goes there too, also where the interpreter had died: a window
scrolled up would give its point back at the next redisplay.

* Moving a cell

=code-cells-mode= puts the cell boundaries into =outline-regexp=. Thus
a cell is an outline subtree, and =outline-move-subtree-down= moves it.
It cuts the text out and puts it back. It also writes the final newline
that a last cell can lack.

=overblock-pycell-move-cell-down= reads what both cells show, moves the
text, and puts each block back on its cell. After the outline move,
point is where the moved cell now begins. Thus the two new ranges are read from the buffer, and
are not counted from the old positions.

The move must know two things:

- The move starts at the boundary line of the cell. =code-cells-mode=
  also puts the headings of the major mode into =outline-regexp=. Thus
  a =def= inside a cell is a heading too, and a move from inside it
  would stop with "Cannot move past superior level".
- The rest of the blocks of the moved cell is swept, because its text
  was cut out.

Point keeps its offset in the cell that moved, so a second click on a
button moves the same cell again. A rendered markdown cell renders
again after the move, because its source lines have moved.

The command signals before it removes anything. outline refuses to
move the first cell up or the last one down, and a refused move leaves
the buffer as it was.

* The live mirror

A ticker runs each 0.2 seconds while a cell runs. It shows the output
so far, a spinner and a stopwatch. The ticker and its bounds belong to
the runner: =overblock-run--output-head= reads the head of the output,
and =overblock-run--total= counts the lines as they arrive.

This package tells what an IPython prompt looks like and how to clean
it away. =overblock-pycell--clean= removes the prompts and the =Out[N]=
labels, and makes a copy that a block can show.

The head of the output is bounded in lines and in characters. The
character bound applies only where no escape sequence starts inside it.
comint-mime sends an image as an escape sequence, and a cut inside it
would lose the figure.

=overblock-pycell--clean= copies through a temporary buffer only where
the text carries a display property. Its =replace-regexp-in-string=
passes first search, because that function copies its argument even
when nothing matches. A result counts its lines once and keeps the
number, so a fold does not count again. A move renders the two cells
that moved, and no other markdown cell.

* Cells with IPython syntax

[[*Results]] tells which syntax only IPython reads. jupytext files hold
such cells.

=overblock-pycell--ipython-syntax-p= reads the buffer with
=syntax-ppss=. Only a line at the top level counts. A continuation line
inside brackets can start with a modulo sign, and a comment can end
with a question mark. A cell of plain Python must not go to IPython
this way, because a shell without IPython answers with a =NameError=.

Such a cell goes to =get_ipython().run_cell=, base64 encoded, which
keeps quotes and newlines safe. A shell without IPython reports that
it does not know =get_ipython=.

* How markdown cells render

The rendering is on the source lines, one piece for each line. Thus a
cell has a height in lines and moves as normal text.

The cell keeps the height of its source, or becomes shorter. A table of
three lines can render as one line, and the spare lines go under a
cloak. The cloak, the pieces and the image on a before-string belong to
the layer ([[file:overblock.org][its notes]]). The converter belongs to
overblock-md ([[file:overblock-md.org][its notes]]).

The live cycle of the layer renders the cells, as it renders the prose
of a Markdown file. =overblock-pycell-render-buffer= renders what is
not rendered yet. The whole buffer goes to the converter in one
process, through =overblock-md-render-regions=, and nothing waits for
it. A cell that the converter fails on shows its source and the source
bar, as a cell that point is in. It goes to the converter again only
after an edit or a click on its render button. The mode starts
its cycle with KEEP, so a rendered cell stays rendered when point
moves into it. A click with =mouse-1=
shows the source until point leaves the cell. A moved cell renders at
once.

Point cannot be on a link, because it never enters a display string.
Thus =overblock-md-follow-link= reads the links of the rendering and
offers them. A click on a link uses the link keymap of
overblock-md.

* Scrolling

A result block is one buffer line, because it is one display string. A
block with an image is harder to scroll through. The reasons are in
[[file:overblock.org][the notes of the layer]].
=overblock-run-pop-output= shows the figure in a buffer of its own.

A rendered markdown cell makes each scroll event more expensive. The
cost comes from the face runs and not from the height. Turn the mode
off to get the plain source and the speed back.

* Known limits

The last cell of a notebook gets a final newline if it has none,
because its result hangs on that newline. This is the only change
=overblock-pycell= makes to the text.

* The tests

=make test= runs the batch suites, one for each file.
=test/overblock-pycell-test.el= belongs to this package. It tests the
clean of the output, the body lines, the cell markers and the folds. It
also tests the edit buffers, the mirror, and the move of a cell. A test
that names only what another package owns is in the suite of that
package.

=make test-live= sends real cells to a real IPython and reads back what
the blocks show. No batch test of this package starts a Python
process. Where no ipython is installed, the target says so and passes.

=make scroll= needs a graphic display. It builds a buffer with markdown
cells and scrolls through it with =pixel-scroll-precision-scroll-up= and
=pixel-scroll-precision-scroll-down=. It uses the default values of the
scroll options. The test fails when:

- The window moves against the direction of the scroll.
- The scroll command signals in the middle of a cell.
- The end of the buffer stays out of reach.

The first check runs on Emacs 30 and later only. On Emacs 29,
=pixel-scroll-precision-scroll-up-page= can leave point outside the
window. Redisplay then recenters, and the window moves back a little.
Emacs 30 puts point back inside the window before redisplay, and the
emacs-29 branch does not have that change. The other two checks run on
each version.
